# Phase 1 Action Plan

## Цель

Превратить текущий прототип в стабильный и честный MVP-контур, на котором можно
безопасно строить реальную генерацию планировок.

## Условие успеха

Пользователь создаёт проект, получает планировку, изменяет её, сохраняет,
повторно открывает и экспортирует именно сохранённое состояние. Метрики и
проверки не создают ложного ощущения точности.

## Принцип исполнения

Phase 1 выполняется тонкими вертикальными срезами. Каждый срез должен оставлять
репозиторий в более проверяемом состоянии, чем до него.

Ralph не запускается до завершения Wave 0, потому что текущие baseline checks
не зелёные.

Конкретный стартовый checklist: [`tasks/bootstrap-baseline.md`](../../tasks/bootstrap-baseline.md).

## Wave 0. Bootstrap Baseline

### Цель

Сделать репозиторий пригодным для безопасной автоматизированной работы.

### Порядок

1. Исправить FastAPI boot blocker на DELETE endpoint с HTTP 204.
2. Ограничить pytest discovery каталогом `tests/`.
3. Исправить синтаксический blocker mypy.
4. Разделить lint, Ruff и mypy ошибки на небольшие исправления.
5. Обновить уязвимую версию Next.js до безопасной совместимой версии.
6. Добавить локальную команду или документированный набор baseline checks.

### Проверки

```bash
npm run lint
npm run build
python -m pytest tests -q
python -m ruff check plana_engine tests
python -m mypy plana_engine
```

### Критерий выхода

Все baseline checks зелёные. Только после этого разрешён Ralph.

## Wave 1. Security and Auth Contract

### Цель

Убрать очевидные security-риски до расширения хранения проектов.

### Порядок

1. Зафиксировать единый способ передачи и хранения сессии.
2. Исправить защиту `/app` и API ownership checks.
3. Удалить JWT secret по умолчанию.
4. Ограничить CORS.
5. Добавить базовые лимиты для auth, AI и upload endpoints.
6. Провести security review изменений.

### Критерий выхода

Неавторизованный пользователь не может открыть защищённый экран, получить или
изменить чужой проект. Приложение не запускается в production без секретов.

## Wave 1B. Editor UX Reliability

Текущий прогресс на 2026-06-04:

- исправлено переключение категорий истории;
- добавлено открытие сохраненных image-assets из истории;
- PDF и архитектурные чертежи не теряют локальное состояние при смене секции;
- ошибки save, history load и delete показаны пользователю;
- добавлен Chromium browser regression test для history restore, PDF section switch и
  ошибок save/history/delete;
- полный аудит видимых кнопок еще не выполнен.

### Цель

Убрать потерю пользовательского контекста и неработающие действия до расширения
редактора и AI-генерации.

### Порядок

1. Провести browser-аудит всех секций, вкладок и видимых кнопок редактора.
2. Зафиксировать владельца состояния генерации, выбранного результата и ошибок.
3. Исправить переключение вкладок истории.
4. Открывать сохранённые PDF, архитектурные чертежи, размещение и интерьеры из
   истории хотя бы как result gallery.
5. Перестать скрывать ошибки save, history load и delete.
6. Сохранить прогресс и результаты генерации при переключении между секциями.
7. Не сбрасывать введённые данные, выбранный вариант и локальные правки без
   явного действия пользователя.
8. Для каждой видимой кнопки реализовать действие, disabled-state с причиной
   или убрать её из MVP-интерфейса.
9. Добавить loading, success, empty, error, retry и cancellation состояния для
   длительных операций.
10. Добавить browser regression test переключения секций во время и после
   генерации.

### Критерий выхода

Пользователь может запустить генерацию, перейти в другую секцию, вернуться и
увидеть тот же прогресс или результат. В основном сценарии нет кнопок, которые
выглядят доступными, но не выполняют понятное действие.

## Wave 1C. Generation Tasks and PDF Workspace

### Цель

Сделать долгие AI-операции и PDF-визуализацию восстановимыми.

### Порядок

1. Расширить `generation_runs` статусами, progress, error и cost metadata.
2. Создавать run до запуска операции, а не после успешного результата.
3. Сохранять исходный PDF, page metadata и generated assets.
4. Восстанавливать PDF workspace после reload и из истории.
5. Добавить retry и cancellation там, где операция это поддерживает.
6. Добавить ownership, file limits и retention policy для PDF assets.

### Критерий выхода

Пользователь может вернуться к PDF-процессу или результату после навигации и
перезагрузки. История показывает успешные и неуспешные задачи честно.

## Wave 2. Canonical Project Persistence

### Цель

Сделать `LayoutProject` сохранённым источником истины.

### Порядок

1. Зафиксировать версию схемы `LayoutProject`.
2. Добавить хранение layout в проекте.
3. Добавить API чтения и сохранения layout.
4. Подключить frontend save/load.
5. Добавить dirty state и понятное состояние сохранения.
6. Добавить тест сохранения и повторного открытия.

### Критерий выхода

После перезагрузки страницы и повторного входа пользователь видит ту же
планировку, которую сохранил.

## Wave 3. One Model Everywhere

### Цель

Убрать расхождения между экраном, аналитикой и экспортом.

### Порядок

1. Передавать текущий layout в DXF export.
2. Проверить IFC export текущего layout.
3. Перевести метрики на текущую модель.
4. Перевести квартирографию и стоимость на текущую модель.
5. Исправить стоимость здания: GFA берётся из layout, а не из площади участка.
6. Показывать источник, уровень цен, исключения и площадочные затраты.
7. Добавить `not_checked` для непроверенных требований.
8. Пометить предварительную стоимость и концептуальный экспорт.

### Критерий выхода

Изменение помещения отражается в метриках и экспортируемом файле. UI не
показывает успешную проверку, если она не запускалась.

## Wave 4. Observability and Delivery

### Цель

Сделать ошибки видимыми команде и защитить качество следующих изменений.

### Порядок

1. Добавить correlation ID в frontend proxy и backend.
2. Добавить структурированные backend logs.
3. Подключить Sentry frontend и backend.
4. Добавить GitHub CI для baseline checks.
5. Добавить browser smoke test основного сценария.
6. Зафиксировать release checklist.

### Критерий выхода

Pull request нельзя слить с красными проверками. Ошибка основного сценария
оставляет диагностируемый след в Sentry и логах.

## Wave 5. Pilot Readiness Review

### Цель

Проверить, что MVP готов к тестированию на реальных данных.

### Порядок

1. Пройти основной user journey в браузере.
2. Проверить DXF, PDF и IFC на одном реальном тестовом проекте.
3. Провести security checkpoint.
4. Проверить пользовательские предупреждения и `not_checked`.
5. Записать известные ограничения.
6. Подготовить короткий сценарий пилотной демонстрации.

### Критерий выхода

Команда может честно показать продукт пилотному пользователю, объяснить
ограничения и получить обратную связь без ручного исправления данных за кадром.

## Роли плагинов в Phase 1

- **Product Design:** проверить основной user journey, dirty state, ошибки и
  предупреждения до UI-изменений.
- **Build Web Apps:** реализовать утверждённые UI-состояния и провести browser
  verification.
- **OpenAI Developers:** в Phase 1 не расширять AI; только добавить лимиты,
  диагностику и измерение существующих AI endpoints.
- **Codex Security:** провести review Wave 1 и Wave 5.
- **Sentry:** реализовать Wave 4 и проверить диагностируемость ошибок.
