# Functional Audit: Real Product Functions

Дата аудита: 2026-06-04.

## Цель

Определить, какие пользовательские функции Plana должны стать реально
рабочими до расширения AI-генерации:

- стоимость на стадии посадки;
- история проектов и генераций;
- PDF-визуализация;
- видимые кнопки и действия интерфейса.

Главный принцип: функция не считается рабочей, если она только запускает запрос
или показывает картинку. Пользователь должен иметь возможность вернуться к
результату, понять его источник, увидеть ошибку и продолжить работу.

## Метод проверки

Проверены:

- frontend-компоненты и обработчики;
- backend endpoints, storage и cost-модули;
- существующие тесты;
- локальный запуск `/`, `/app`, `/projects`, `/api/health` и `/docs`.

Локальные HTTP endpoints отвечают `200`. Полный браузерный click-through в этой
сессии не выполнен: Browser runtime не предоставил callable-инструмент, а
Playwright не установлен в проекте. Поэтому выводы ниже основаны на
авторитетном поведении кода и должны быть подтверждены browser regression tests
во время реализации.

## Краткий вывод

Сейчас Plana имеет много отдельных работающих вычислений и AI endpoints, но не
имеет надёжного рабочего пространства проекта.

Пользователь может получить результат, но не всегда может:

- сохранить его без скрытой ошибки;
- открыть его из истории;
- продолжить процесс после переключения секции;
- понять, соответствует ли стоимость реальному зданию;
- доверять активной кнопке.

До новых генераторов нужно стабилизировать именно эти продуктовые функции.

## Подтверждённые проблемы

### F-001. Стоимость на посадке считается от площади участка

**Статус:** критично.

В `SiteTab` панель получает `siteW` и `siteD`, а `CostEstimatePanel` вычисляет
`GFA = width × depth × floors`. Это означает, что стоимость зависит от площади
участка, а не от пятна или модели здания.

Доказательства:

- `src/app/app/page.tsx:1470`;
- `src/components/CostEstimatePanel.tsx`;
- backend уже поддерживает путь `layout + n_floors`, но frontend его не
  использует: `engine/plana_engine/api/main.py:2803`.

### F-002. Текущие ставки стоимости являются placeholder

**Статус:** критично для доверия.

`aggregate_cost.py` прямо помечает ставки как `official=False`,
`2025-placeholder` и предупреждает о необходимости заменить их на
лицензированный источник.

Доказательства:

- `engine/plana_engine/cost/aggregate_cost.py:49`;
- `engine/plana_engine/cost/aggregate_cost.py:56`;
- `engine/plana_engine/cost/aggregate_cost.py:190`.

Вывод: текущий результат нельзя называть реальной сметой. Это только
укрупнённая концептуальная оценка.

### F-003. QTO существует, но не подключён к пользовательской стоимости

**Статус:** частично реализовано.

Backend умеет получать объёмы стен, перекрытий, помещений, дверей и окон из IFC.
Также есть тесты QTO. Но нет material mapping, unit rates, endpoint для ведомости
объёмов и frontend-представления.

Доказательства:

- `engine/plana_engine/cost/qto.py`;
- `engine/plana_engine/cost/aggregate_cost.py:248`;
- `engine/tests/test_cost_qto.py`;
- `engine/tests/test_floorplan_ifc_qto.py`.

### F-004. Переключение секций уничтожает состояние PDF-визуализации

**Статус:** критично.

`PdfVizTab` хранит загруженный PDF, страницы, очередь, статусы и результаты в
локальном React state. Компонент условно монтируется только при активной
PDF-вкладке. При переходе в другую секцию он размонтируется, а при возврате
создаётся заново.

Доказательства:

- `src/components/PdfVizTab.tsx:76`;
- `src/app/app/page.tsx:1133`.

### F-005. История PDF и архитектурных чертежей не открывает результат

**Статус:** критично.

Обработчик истории для `pdf_viz` и `arch_drawings` только переключает вкладку.
Сохранённые изображения не передаются в соответствующий workspace.

Доказательства:

- `src/app/app/page.tsx:902`;
- `src/app/app/page.tsx:906`.

Для PDF дополнительно не сохраняются исходный PDF, page previews и metadata
страниц, поэтому полноценное восстановление невозможно на текущей схеме.

### F-006. Вкладки внутри панели истории визуально кликаются, но не переключаются

**Статус:** критично.

`HistoryPanel` вычисляет `activeTab = currentTab ?? selectedTab`. Родитель всегда
передаёт `currentTab={tab}`, поэтому клик меняет `selectedTab`, но это значение
не используется.

Доказательства:

- `src/components/HistoryPanel.tsx:186`;
- `src/app/app/page.tsx:1150`.

### F-007. Не все типы генераций восстанавливаются при открытии проекта

**Статус:** критично.

При загрузке проекта восстанавливаются только `ai_plans`, `viz_exterior`,
`viz_floor` и `site`. Не восстанавливаются `viz_interior`, `placement`,
`pdf_viz` и `arch_drawings`.

Доказательство:

- `src/app/app/page.tsx:346`.

### F-008. Generation run не является реальной задачей

**Статус:** архитектурный риск.

`generation_runs` создаётся после успешной генерации, внутри
`autoSaveGeneration`. У run нет статусов `queued`, `running`, `failed`,
progress или error. Поэтому история не может показывать длительный процесс,
восстанавливать его после навигации или объяснять отказ.

Доказательства:

- `src/app/app/page.tsx:434`;
- `engine/plana_engine/auth/db.py`;
- `engine/plana_engine/projects/router.py`.

### F-009. Ошибки сохранения и истории скрываются

**Статус:** критично для доверия.

Ряд операций использует пустые `catch`, включая сохранение ассетов, обновление
проекта, загрузку истории и удаление проекта. UI может показать успех или
удалить карточку локально, хотя backend-операция не завершилась.

Доказательства:

- `src/app/app/page.tsx:411`;
- `src/app/app/page.tsx:425`;
- `src/app/app/page.tsx:461`;
- `src/components/HistoryPanel.tsx:192`;
- `src/app/projects/page.tsx:148`.

### F-010. Часть интерфейса является честно отключённым demo, часть — нет

**Статус:** требует инвентаризации.

В архитектурном редакторе инструменты стен, дверей, окон, лестниц, помещений,
мебели, размеров и ластика отключены. Это лучше, чем ложная работа, но
интерфейс всё равно обещает больше, чем MVP.

Доказательства:

- `src/components/ArchitecturalDrawingsTab.tsx:458`;
- `src/components/editor/LeftToolbar.tsx`;
- `src/components/editor/ModeTabs.tsx`.

Отдельный риск: кнопка `AI Виз` архитектурного чертежа вызывает режим `A`, не
передавая сам план как референс. Результат может быть тематической картинкой, а
не визуализацией видимого проекта.

Доказательство:

- `src/components/ArchitecturalDrawingsTab.tsx:300`.

### F-011. Оценка стоимости AI в PDF зашита константами

**Статус:** средний риск.

PDF UI показывает стоимость из локальных констант, без фактического usage,
модели, размера изображения и цены провайдера.

Доказательства:

- `src/components/PdfVizTab.tsx:44`;
- `src/components/PdfVizTab.tsx:260`.

Дополнительно engine по умолчанию использует `gpt-image-2`, а комментарий UI
описывает `gpt-image-1`.

Доказательства:

- `engine/plana_engine/visualizer/grok_client.py:20`;
- `engine/plana_engine/visualizer/openai_client.py:48`.

Актуальные тарифы OpenAI зависят от модели и image tokens, поэтому константа
уже не является надёжным источником.

### F-012. Тесты доказывают вычисления, но не доказывают пользовательские потоки

**Статус:** высокий риск регрессий.

Cost-тесты проверяют математику placeholder-оценки и QTO. Не найдено browser или
frontend regression tests для истории, PDF workspace, переключения секций и
видимых кнопок.

Доказательства:

- `engine/tests/test_cost_aggregate.py`;
- `engine/tests/test_cost_endpoint.py`;
- `engine/tests/test_cost_qto.py`;
- frontend test workflow для указанных сценариев не найден в коде.

## Что должно стать реальными функциями

### RF-1. Project Workspace

Проект должен хранить не только параметры и картинки, но и текущий workspace:

- канонический `LayoutProject`;
- выбранный вариант;
- состояние секций;
- ссылки на исходные файлы;
- генерационные задачи;
- результаты и ошибки;
- версия и дата сохранения.

### RF-2. Generation Tasks

Каждая долгая операция должна быть задачей:

```text
queued -> running -> succeeded | failed | cancelled
```

Задача хранит:

- тип операции;
- project ID и user ID;
- входной snapshot;
- progress;
- provider/model;
- result assets;
- error;
- latency;
- оценочную и фактическую стоимость.

### RF-3. Openable History

История должна открывать результат, а не просто показывать thumbnail.

Для каждого поддерживаемого типа:

- открыть результат в правильной секции;
- восстановить входные параметры;
- показать связанные ассеты;
- показать статус и ошибку;
- позволить повторить или продолжить;
- не терять текущую несохранённую работу без предупреждения.

### RF-4. PDF Workspace

PDF-визуализация должна быть отдельным сохраняемым workspace:

- исходный PDF как project asset;
- metadata страниц;
- превью страниц;
- выбранный тип, режим и hint;
- status каждой страницы;
- generated result asset;
- повторное открытие из проекта и истории;
- retry отдельной страницы;
- явная стоимость до запуска и фактическая стоимость после.

### RF-5. Investment Cost, Not Fake Smeta

Для MVP корректное название: **предварительная инвестиционная стоимость** или
**укрупнённая оценка стоимости**, а не «реальная смета».

Рабочий MVP-расчёт должен:

- брать GFA и пятно из текущей модели здания, не из участка;
- показывать источник, регион, уровень цен и дату ставки;
- отдельно считать здание, подземный паркинг, благоустройство, внешние сети и
  другие площадочные затраты;
- позволять ручные корректировки с пояснением;
- показывать диапазон точности и исключения;
- сохраняться вместе с версией проекта;
- сравнивать варианты по одинаковой методике.

Следующий уровень после MVP:

- QTO из IFC/LayoutProject;
- material/work mapping;
- лицензированные unit rates;
- ведомость объёмов;
- экспорт для проверки сметчиком.

### RF-6. Action Contract

Каждая видимая кнопка должна иметь один из трёх статусов:

1. Работает и имеет проверяемый результат.
2. Disabled с понятной причиной и условием доступности.
3. Скрыта из MVP.

Нельзя:

- проглатывать ошибку;
- показывать success до подтверждения backend;
- оставлять кнопку, которая только переключает пустой экран;
- выдавать тематическую AI-картинку за результат текущей модели.

## Рекомендуемый порядок реализации

### Slice 1. Reliability Hotfix

Цель: убрать самые болезненные разрывы без новой архитектуры.

Статус на 2026-06-04: реализован первый hotfix. История переключается, сохраненные
`pdf_viz`, `arch_drawings`, `placement` и `viz_interior` assets открываются как
result gallery, ошибки save/history/delete больше не проглатываются, а PDF и
редактор архитектурных чертежей сохраняют локальную сессию при переключении
секций. Полное восстановление исходного PDF и редактируемой модели остается в
Slice 2. Chromium e2e покрывает переключение категорий истории, восстановление
AI-планов, экстерьера, плана с мебелью, посадки, PDF, архитектурных чертежей,
размещения и интерьера, сохранение PDF-сессии между секциями и видимые ошибки
save/history/delete. В ходе проверки дополнительно исправлено переключение
активного режима при restore `viz_floor`.

Задачи:

1. Исправить переключение вкладок истории.
2. Добавить restore для сохранённых `pdf_viz`, `arch_drawings`, `placement` и
   `viz_interior` ассетов хотя бы как result gallery.
3. Перестать скрывать ошибки save, history load и delete.
4. Поднять PDF state в родительский project workspace, чтобы переход между
   секциями не сбрасывал текущую сессию.
5. Провести инвентаризацию видимых кнопок основного сценария.

Основные файлы:

- `src/app/app/page.tsx`;
- `src/components/HistoryPanel.tsx`;
- `src/components/PdfVizTab.tsx`;
- `src/app/projects/page.tsx`;
- `src/lib/projects.ts`.

Критерий готовности:

Пользователь переключает секции, открывает результат из истории и всегда видит
ошибку сохранения или загрузки.

### Slice 2. Persistent Generation Tasks and PDF Workspace

Цель: сделать долгие операции восстановимыми.

Задачи:

1. Расширить `generation_runs` статусами, progress, error и cost metadata.
2. Создавать run до запуска операции.
3. Сохранять исходный PDF и page metadata как assets.
4. Восстанавливать PDF workspace после reload и из истории.
5. Добавить retry/cancel для поддерживаемых задач.

Основные файлы:

- `engine/plana_engine/auth/db.py`;
- `engine/plana_engine/projects/router.py`;
- `engine/plana_engine/projects/storage.py`;
- `src/lib/projects.ts`;
- `src/components/PdfVizTab.tsx`;
- `src/app/app/page.tsx`.

Критерий готовности:

Пользователь закрывает или переключает секцию во время PDF-обработки, затем
возвращается и видит актуальный статус или сохранённый результат.

### Slice 3. Model-Derived Investment Cost

Цель: сделать стоимость полезной для сравнения вариантов.

Задачи:

1. Исправить вход: использовать текущий layout/building footprint.
2. Зафиксировать cost schema и категории площадочных затрат.
3. Подключить versioned rate dataset с источником и уровнем цен.
4. Добавить manual overrides и audit trail.
5. Сохранять cost snapshot с проектом.
6. Показывать сравнение стоимости вариантов.

Основные файлы:

- `engine/plana_engine/cost/aggregate_cost.py`;
- `engine/plana_engine/cost/qto.py`;
- `engine/plana_engine/api/main.py`;
- `src/components/CostEstimatePanel.tsx`;
- `src/lib/engine.ts`;
- будущий versioned dataset стоимости.

Критерий готовности:

Изменение пятна или этажности здания меняет стоимость; изменение только размера
участка не меняет стоимость здания. Пользователь видит источник и исключения.

### Slice 4. QTO-Based Cost Foundation

Цель: перейти от ставки на м² к проверяемым объёмам.

Задачи:

1. Подключить QTO к текущему `LayoutProject`.
2. Добавить mapping элементов к материалам и работам.
3. Подключить лицензированные или утверждённые ставки.
4. Добавить ведомость объёмов и экспорт.
5. Проверить расчёт с аттестованным сметчиком.

Критерий готовности:

Сметчик может проследить строку стоимости до объёма модели, ставки, источника и
версии данных.

## Обязательные тесты

- browser: переключение секций во время и после генерации;
- browser: вкладки истории реально меняют список;
- browser: открытие каждого поддерживаемого типа результата из истории;
- browser: PDF upload -> generation -> другая секция -> возврат -> результат;
- browser: save/delete/history load error states;
- API: run lifecycle и ownership;
- API: PDF source/page metadata persistence;
- cost: GFA из layout, а не из участка;
- cost: versioned rate source и manual override;
- cost: site works categories;
- regression: видимые enabled-кнопки основного сценария имеют ожидаемое действие.

## Что не обещать пользователю

- сертифицированную смету;
- точную стоимость без утверждённых ставок и исходных данных;
- восстановление результата, если его source и metadata не сохранены;
- рабочий CAD-инструмент только потому, что кнопка нарисована;
- соответствие AI-визуализации текущей модели без model-derived reference.

## Решения, которые нужно утвердить

1. Пользователю нужна укрупнённая инвестиционная оценка или локальная смета?
2. Кто предоставляет и лицензирует ставки стоимости?
3. Какие площадочные затраты обязательны для первого пилота?
4. Нужно ли хранить исходные PDF-файлы, и какой срок хранения допустим?
5. Какие кнопки архитектурного редактора входят в MVP, а какие скрываются?

## Роли подключённых инструментов

- **Product Design:** аудит основного user journey и обещаний интерфейса.
- **Build Web Apps:** browser regression tests и исправление frontend-потоков.
- **OpenAI Developers:** usage accounting, модель, лимиты и фактическая
  стоимость AI-задач.
- **Codex Security:** ownership, лимиты, retention и безопасная обработка PDF.
- **Sentry:** ошибки сохранения, генерации, PDF и истории с correlation ID.
- **GitHub:** issues, milestones, CI и review по каждому slice.
- **Notion:** решения по ставкам, PDF retention и функциям MVP.
