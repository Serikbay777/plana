# Product Validation Plan

## Цель

До расширения генератора и CAD-пайплайна доказать, что выбранный пользователь
испытывает проблему, понимает результат Plana и готов использовать его в
реальном процессе.

## Гипотезы

### H-001. Скорость

Девелоперу важно получить первый обоснованный вариант типового этажа быстрее,
чем через текущий ручной процесс.

### H-002. Сравнение

Пользователю важнее сравнить несколько вариантов по понятным показателям, чем
получить одну красивую визуализацию.

### H-003. Передача

Редактируемый DXF или IFC повышает ценность результата сильнее, чем статичная
картинка или PDF.

### H-004. Ограничения

Предварительные предупреждения полезны, если система ясно отделяет проверенное
от непроверенного и показывает источник правила.

### H-005. Экономика

Укрупнённая оценка полезна для сравнения вариантов, даже если она не является
сметой.

## Участники исследования

Минимальный набор:

- 5-7 представителей девелопера;
- 3-5 архитекторов, работающих с ранней стадией жилых проектов;
- 1-2 специалиста по нормам Казахстана;
- 1-2 специалиста по экономике строительства.

## Что собрать

- реальные обезличенные briefs;
- DXF-контуры участков;
- примеры типовых этажей;
- таблицы квартирографии;
- примеры файлов, которые передаются между девелопером и архитектором;
- список решений, принимаемых на ранней стадии;
- список причин, по которым варианты отклоняются.

## Формат интервью

1. Попросить пользователя показать последний реальный проект.
2. Разобрать текущий путь от исходных данных до решения.
3. Зафиксировать время, участников, файлы и ручные пересчёты.
4. Показать текущий Plana без обещаний будущих функций.
5. Попросить пользователя выполнить основной сценарий.
6. Спросить, какой результат он готов передать коллеге.
7. Зафиксировать, за что пользователь готов платить и чему не доверяет.

## Признаки подтверждения

- пользователи называют проблему без подсказки;
- минимум 3 пользователя готовы дать реальные данные для пилота;
- минимум 3 пользователя считают редактируемый экспорт полезным;
- пользователи понимают разницу между предварительной проверкой и согласованием;
- основной сценарий можно выполнить без постоянного объяснения интерфейса;
- пилот экономит измеримое время или снижает количество ручных итераций.

## Признаки опровержения

- пользователю нужна рабочая документация, а не концепция;
- типовой этаж не является значимым решением;
- без полного ГПЗУ или BIM результат не имеет ценности;
- пользователь доверяет только работе архитектора и не использует варианты;
- экспорт не пригоден для продолжения работы;
- стоимость продукта выше ценности сэкономленного времени.

## Выходы Phase 0

- сводка интервью в Notion;
- обезличенный набор fixtures в контролируемом хранилище;
- обновлённые решения в `DECISIONS.md`;
- подтверждённые метрики пилота;
- утверждённый PRD для Phase 1.
