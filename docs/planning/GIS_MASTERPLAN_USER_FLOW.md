# GIS Masterplan User Flow

Дата: 2026-06-11
Статус: целевой функциональный сценарий

## 1. Зачем этот документ

Этот документ описывает, как должен работать будущий функционал Plana шаг за шагом.

Главная идея:

```text
Пользователь выбирает реальный участок на карте -> переходит в управление участком -> собирает посадку -> система проверяет нормы -> считает стоимость -> сохраняет проект -> экспортирует результат.
```

Это не просто карта и не просто калькулятор. Это workflow для раннего masterplanning: быстро понять, что можно построить на конкретном участке, какие есть ограничения, какие сценарии посадки возможны и сколько это примерно стоит.

## 2. Главный пользовательский сценарий

### Step 1 - Пользователь открывает карту

Пользователь заходит в раздел:

```text
/map
```

Он видит:

- карту города;
- участки из GIS;
- соседние здания;
- красные линии;
- подсказку "приблизьте карту и выберите участок".

Смысл шага:

Пользователь начинает не с пустой формы, а с реального городского контекста.

## 3. Step 2 - Пользователь выбирает участок

Пользователь кликает на участок на карте.

Система делает:

1. Берет GeoJSON выбранного участка.
2. Достает внешний контур участка.
3. Отправляет контур в backend.
4. Backend подтягивает GIS context:
   - соседние здания;
   - дороги / проезды;
   - красные линии;
   - функциональную зону;
   - базовые свойства участка.
5. Frontend переводит геометрию в локальные метры.
6. Система показывает right panel с первичной информацией.

Пользователь видит:

- название / описание участка;
- площадь участка;
- назначение / функциональную зону;
- бейджи источников данных;
- предупреждение, если участок похож на соцобъект или не подходит под жилье;
- кнопку `Перейти к управлению участком`.

## 4. Step 3 - Пользователь переходит в управление участком

После выбора участка появляется действие:

```text
Открыть workspace / Управлять участком
```

Пользователь нажимает кнопку.

Система создает временный masterplan draft:

- фиксирует выбранный участок;
- сохраняет контур участка;
- сохраняет GIS context snapshot;
- создает пустой список объектов посадки;
- открывает отдельный workspace.

Workspace должен быть отдельным рабочим режимом, а не маленькой панелью справа.

## 5. Step 4 - Открывается Parcel Workspace

Пользователь видит рабочий экран:

```text
┌───────────────────────────────┬───────────────────────────────┐
│ Карта / контекст              │ Панель параметров              │
│                               │                               │
│ Участок + красные линии       │ ТЭП                           │
│ Соседи + дороги               │ Нормы                         │
│                               │ Стоимость                     │
├───────────────────────────────┴───────────────────────────────┤
│ Редактор посадки / canvas                                     │
└───────────────────────────────────────────────────────────────┘
```

В workspace есть:

- locked boundary участка;
- красные линии;
- соседние здания;
- дороги / проезды;
- панель объектов;
- панель параметров;
- панель нормоконтроля;
- панель стоимости;
- кнопки сохранения и экспорта.

Смысл шага:

Участок становится не просто selected feature на карте, а полноценным проектным объектом.

## 6. Step 5 - Пользователь выбирает режим работы

После открытия workspace пользователь выбирает один из режимов:

### Manual mode

Пользователь сам добавляет объекты:

- жилой корпус;
- второй жилой корпус;
- школа;
- детский сад;
- паркинг;
- коммерция;
- двор;
- озеленение.

### Generate variants mode

Система предлагает стартовые варианты:

- максимальный GFA;
- сбалансированный двор;
- смешанное использование;
- вариант с соцобъектом.

Пользователь выбирает вариант и дальше редактирует руками.

### Hybrid mode

Пользователь задает желаемые параметры, система предлагает схему, пользователь доводит ее вручную.

## 7. Step 6 - Пользователь добавляет объекты на участок

В левой или верхней панели есть object palette:

- `Жилой корпус`;
- `Школа`;
- `Детский сад`;
- `Паркинг`;
- `Коммерция`;
- `Озеленение`;
- `Двор`.

Пользователь выбирает объект и добавляет его на canvas.

У каждого объекта есть параметры:

- тип;
- название;
- ширина;
- глубина;
- этажность;
- поворот;
- площадь пятна;
- GFA;
- назначение;
- класс здания;
- дополнительные параметры.

Пример:

```text
Жилой корпус A
- 18 этажей
- 56 x 22 м
- comfort class
- mixed-use ground floor: yes
```

## 8. Step 7 - Пользователь двигает, масштабирует и вращает объекты

Пользователь может:

- переместить объект;
- изменить размер;
- повернуть;
- дублировать;
- удалить;
- изменить этажность;
- изменить назначение.

Каждое изменение сразу пересчитывает:

- площадь застройки;
- GFA;
- КИТ / FAR;
- процент застройки;
- озеленение;
- паркинг;
- потенциальную стоимость.

## 9. Step 8 - Система проверяет правила в реальном времени

При каждом изменении система запускает проверки.

### Boundary check

Если объект выходит за границу участка:

- объект подсвечивается красным;
- появляется ошибка:

```text
Корпус выходит за границы участка.
```

### Red lines check

Если объект пересекает красную линию:

- линия подсвечивается;
- объект подсвечивается;
- появляется ошибка:

```text
Пятно здания пересекает красную линию.
```

### Neighbor gap check

Если объект слишком близко к соседнему зданию:

- появляется warning:

```text
Расстояние до соседнего здания меньше минимального противопожарного разрыва.
```

### FAR / KIT check

Если превышен КИТ:

```text
КИТ превышает допустимое значение.
```

### Coverage check

Если превышен процент застройки:

```text
Процент застройки превышает лимит.
```

### Zoning check

Если пользователь ставит жилой корпус на участок, который по зоне выглядит как социальный или коммерческий:

```text
Назначение участка требует уточнения по ПДП/ГПЗУ.
```

### Parking / green check

Если не хватает паркинга или озеленения:

```text
Не хватает машиномест по выбранному классу жилья.
```

```text
Озеленение ниже расчетного ориентира.
```

## 10. Step 9 - Пользователь смотрит ТЭП

Система показывает ТЭП по всей посадке:

- площадь участка;
- площадь застройки;
- процент застройки;
- GFA;
- подземная площадь;
- КИТ / FAR;
- количество корпусов;
- количество квартир;
- машиноместа;
- озеленение;
- коммерческая площадь;
- соцобъекты;
- строительный объем.

Каждая цифра должна иметь источник:

- `GIS` - пришло из карты;
- `Расчет` - рассчитано системой;
- `Норма` - взято из нормативной базы;
- `Ручной ввод` - изменено пользователем;
- `AI` - предложено AI и подтверждено пользователем.

## 11. Step 10 - Пользователь генерирует варианты

Если пользователь нажимает:

```text
Сгенерировать варианты посадки
```

Система создает несколько схем:

### Variant A - Max GFA

Цель: максимально использовать участок.

Особенности:

- высокая плотность;
- максимальный КИТ в рамках ограничений;
- может иметь больше warnings.

### Variant B - Balanced Courtyard

Цель: сбалансированный двор и нормальная плотность.

Особенности:

- лучшее качество двора;
- меньше рисков по нормам;
- ниже GFA, чем Max GFA.

### Variant C - Mixed Use / Social

Цель: учесть коммерцию, соцобъект или смешанное назначение.

Особенности:

- часть участка под детсад/школу/коммерцию;
- ниже жилая площадь;
- выше соответствие городскому контексту.

Пользователь видит сравнение:

- GFA;
- стоимость;
- warnings/errors;
- FAR;
- coverage;
- parking;
- green area;
- feasibility signal.

## 12. Step 11 - Пользователь выбирает вариант и редактирует

Пользователь выбирает один вариант как базовый.

После выбора:

- вариант становится editable;
- объекты можно двигать;
- можно менять этажность;
- можно добавлять новые объекты;
- можно удалять лишние объекты.

Система продолжает проверять нормы и стоимость в реальном времени.

## 13. Step 12 - Система считает стоимость

Стоимость должна считаться от фактической посадки, а не от абстрактной формы.

В cost model передаются:

- участок;
- площадь участка;
- GFA;
- underground GFA;
- количество этажей;
- класс жилья;
- количество корпусов;
- паркинг;
- коммерция;
- соцобъекты;
- красные линии;
- соседние здания;
- функциональная зона;
- гео-риск;
- missing data warnings.

Пользователь видит:

- expected cost;
- low / high range;
- buckets;
- included / excluded items;
- assumptions;
- source metadata;
- warnings.

Важно:

AI может объяснять стоимость, но не должен сам придумывать итоговую цифру. Итоговая цифра должна идти из расчетной модели.

## 14. Step 13 - Пользователь сохраняет проект

Пользователь нажимает:

```text
Сохранить проект
```

Система сохраняет:

- выбранный участок;
- исходный GeoJSON;
- локальную геометрию;
- GIS context snapshot;
- список объектов;
- параметры объектов;
- validation result;
- cost result;
- source metadata;
- дату последнего обновления GIS data.

После этого проект появляется в истории.

## 15. Step 14 - Пользователь открывает проект из истории

Пользователь заходит в историю проектов.

Он может открыть сохраненный masterplan.

Система восстанавливает:

- участок;
- объекты;
- параметры;
- нормоконтроль;
- стоимость;
- warnings;
- source metadata.

Если GIS context устарел, система показывает:

```text
GIS context был загружен 12 дней назад. Обновить данные?
```

## 16. Step 15 - Пользователь экспортирует результат

Пользователь может экспортировать:

- PDF report;
- CSV cost report;
- DXF site plan;
- IFC massing model;
- JSON project data.

Минимальный MVP export:

- PDF / CSV с ТЭП, нормами, стоимостью и источниками данных;
- GeoJSON / JSON для внутреннего обмена;
- DXF позже, когда геометрия объектов станет стабильной.

## 17. Как это должно выглядеть для пользователя

Пользовательское ощущение должно быть таким:

```text
Я выбрал реальный участок.
Система поняла его ограничения.
Я быстро накидал корпуса и соцобъекты.
Система сразу показала, где нельзя строить.
Я получил ТЭП, риски и стоимость.
Я сохранил проект и могу показать его руководству.
```

## 18. Что должно происходить внутри системы

Внутренний pipeline:

```text
Map click
  -> GeoJSON parcel
  -> ring WGS84
  -> import site context
  -> local metric projection
  -> masterplan draft
  -> object editing
  -> metrics calculation
  -> validation runner
  -> cost adapter
  -> report/export
  -> project save
```

## 19. Минимальная версия для MVP

MVP не должен пытаться сделать сразу полный BIM/Urban CAD.

Минимально достаточно:

1. Выбор участка на карте.
2. Переход в workspace.
3. Locked boundary участка.
4. Добавление прямоугольных объектов.
5. Move / resize / rotate.
6. Realtime ТЭП.
7. Realtime validation:
   - boundary;
   - red lines;
   - neighbor gap;
   - FAR;
   - coverage.
8. Связь со стоимостью.
9. Сохранение проекта.
10. Экспорт краткого отчета.

## 20. Что не делать в первой версии

В первой версии не нужно:

- полноценный BIM editor;
- сложные криволинейные корпуса;
- точный DWG production export;
- автоматическое юридическое заключение;
- обучение ML модели;
- официальный расчет сметы;
- автоматическая экспертиза норм.

Сначала нужен рабочий, понятный и честный early-stage masterplanning workflow.

## 21. Главная продуктовая ценность

Этот функционал превращает Plana из генератора картинок и форм в инструмент принятия девелоперских решений.

Ключевая ценность:

```text
Быстро понять, что можно построить на конкретном участке, какие ограничения есть, какой вариант посадки лучше и сколько это примерно стоит.
```

## 22. Следующий практический шаг

Рекомендуемый ближайший слайс:

```text
Parcel Workspace MVP
```

В него входит:

- кнопка `Открыть workspace` после выбора участка;
- отдельный экран workspace;
- отображение locked boundary;
- отображение red lines / neighbors;
- добавление одного rectangular residential building;
- move / resize;
- пересчет ТЭП;
- базовая проверка boundary / coverage / FAR.

После этого можно добавлять:

- несколько объектов;
- школы / детсады / паркинг;
- генерацию вариантов;
- cost integration;
- сохранение проекта.
