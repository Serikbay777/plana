# Delivery Roadmap

## Phase 0. Product Lock

### Цель

Зафиксировать пользователя, типологию, основной результат и границы MVP.

### Задачи

- провести 5-10 интервью с целевыми пользователями;
- получить 5-10 реальных примеров исходных данных и результатов;
- утвердить решения из `DECISIONS.md`;
- согласовать основной user journey;
- определить метрики пилота;
- подготовить PRD и Ralph stories для Phase 1.

### Критерий готовности

Founder, product owner и техническая команда одинаково формулируют, что входит
в MVP, что не входит и по каким метрикам пилот считается успешным.

## Phase 1. Stable Honest MVP

### Цель

Сделать существующий сквозной сценарий надёжным и честным.

### Порядок

1. Исправить запуск backend, pytest discovery, lint, Ruff и mypy.
2. Исправить auth, secrets, CORS и базовые лимиты.
3. Убрать потерю состояния между секциями и неработающие кнопки.
4. Сделать историю и PDF workspace восстановимыми.
5. Сохранять канонический `LayoutProject`.
6. Перевести метрики, стоимость и экспорты на текущую сохранённую модель.
7. Исправить DXF export текущего layout.
8. Добавить статусы `not_checked` и предупреждения в UI.
9. Добавить CI, Sentry и структурированные логи.

### Основные файлы

- `engine/plana_engine/api/main.py`
- `engine/plana_engine/projects/`
- `engine/plana_engine/domain/`
- `engine/plana_engine/cad/`
- `src/lib/engine.ts`
- `src/lib/projects.ts`
- `src/components/ArchitecturalDrawingsTab.tsx`
- `src/components/*Panel.tsx`

### Тесты

- API boot test;
- auth tests;
- browser test сохранения прогресса и результатов при переключении секций;
- browser-аудит доступных кнопок основного сценария;
- browser test открытия каждого поддерживаемого результата из истории;
- browser test PDF upload -> generation -> другая секция -> возврат;
- project save and reopen test;
- edited layout export test;
- frontend build and lint;
- browser smoke test основного сценария.

### Критерий готовности

Пользователь не теряет изменения, а каждый экспорт и показатель соответствует
видимой сохранённой версии проекта.

## Phase 2. Real Layout Generation

### Цель

Выдавать несколько воспроизводимых, объяснимых и сравнимых вариантов.

### Порядок

1. Расширить схему типового жилого этажа.
2. Преобразовать brief в подтверждаемые требования.
3. Формализовать constraints и scoring.
4. Добавить solver или детерминированный search.
5. Генерировать и ранжировать 3-5 кандидатов.
6. Подключить безопасный AI edit flow.
7. Добавить evals и сравнение качества.

### Основные файлы

- `engine/plana_engine/layout_schema.py`
- `engine/plana_engine/visualizer/brief_parser.py`
- `engine/plana_engine/visualizer/layout_generator.py`
- `engine/plana_engine/visualizer/layout_chat_editor.py`
- новые модули `constraints`, `solver`, `scoring`
- frontend flow генерации и сравнения вариантов

### Тесты

- deterministic generation;
- geometry invariants;
- scoring fixtures;
- brief parsing evals;
- edit operation validation;
- browser test выбора и редактирования варианта.

### Критерий готовности

Одинаковый brief и seed дают воспроизводимые варианты, а пользователь понимает,
почему варианты различаются и какие ограничения нарушены.

## Phase 3. CAD, PDF and IFC Pipeline

### Цель

Сделать результаты пригодными для продолжения работы в CAD/BIM.

### Порядок

1. Зафиксировать DXF layer convention и единицы измерения.
2. Довести DXF export и добавить round-trip tests.
3. Сделать PDF-листы в масштабе.
4. Реализовать семантический DXF import.
5. Улучшить IFC export и свойства.
6. Добавить IFC import по ограниченному профилю.
7. Решить DWG через отдельный конвертер.

### Тесты

- golden files;
- round-trip geometry;
- открытие файлов в целевых инструментах;
- проверка единиц, слоёв и стабильных ID;
- ошибки на неподдерживаемых входах.

### Критерий готовности

Архитектор может открыть экспорт, проверить геометрию и продолжить
концептуальную работу без перестроения результата с нуля.

## Phase 4. Kazakhstan Validators

### Цель

Создать прозрачную систему поддержки решений по нормам Казахстана.

### Порядок

1. Утвердить источники и версии норм с экспертом.
2. Исправить setbacks и добавить FAR.
3. Добавить помещения, коридоры, лестницы, лифты и эвакуацию.
4. Добавить доступность и парковки.
5. Реализовать комнатную инсоляцию.
6. Показывать нарушения на плане.

### Тесты

- по одному положительному и отрицательному кейсу на правило;
- fixtures от архитектора;
- versioned norm data;
- regression suite на реальных проектах.

### Критерий готовности

Каждая проверка имеет источник, версию, тест и визуально показывает место
нарушения. Непроверенные требования явно отмечены.

## Phase 5. Production Beta

### Цель

Безопасно отдать продукт первым платящим пользователям.

### Порядок

1. PostgreSQL и миграции.
2. S3-совместимое хранилище.
3. Очередь фоновых задач.
4. Версии проектов и аудит.
5. Квоты, биллинг и контроль AI-стоимости.
6. Мониторинг, резервные копии и runbooks.
7. Controlled beta и продуктовая аналитика.

### Критерий готовности

Есть восстановление после ошибок, измеримые SLO, контролируемые затраты,
резервные копии и понятный процесс поддержки пилотных клиентов.
