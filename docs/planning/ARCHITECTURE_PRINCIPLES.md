# Architecture Principles

## 1. Один источник истины

`LayoutProject` должен стать сохранённой канонической моделью редактируемого
проекта. Все представления и расчёты должны быть производными от него.

Производные данные:

- SVG и canvas представление;
- доменная модель для валидаторов;
- метрики и стоимость;
- DXF, PDF и IFC;
- AI-контекст для объяснений и правок.

Нельзя пересобирать экспорт из исходных form inputs, если пользователь уже
изменил layout.

## 2. Разделение слоёв

```text
Input adapters
  -> Canonical project model
  -> Generators and editors
  -> Validators and analytics
  -> Output adapters
  -> UI views
```

Каждый адаптер обязан явно сообщать, какие данные он сохранил, потерял или не
смог распознать.

## 3. AI не является базой данных или геометрическим ядром

LLM может:

- разбирать brief;
- объяснять варианты;
- предлагать ограничения;
- преобразовывать пользовательскую команду в безопасные операции.

LLM не должен:

- быть единственным источником геометрии;
- возвращать целую модель без проверки;
- объявлять соответствие нормам;
- незаметно изменять заблокированные элементы;
- создавать экспорт напрямую.

## 4. Детерминированная геометрия

Геометрические операции, scoring и валидаторы должны быть воспроизводимыми.
Одинаковые входные данные и seed должны давать одинаковый результат.

## 5. Версионирование модели

Схема проекта должна иметь версию. Изменение схемы требует:

- миграции сохранённых проектов;
- тестов совместимости;
- обновления импортёров и экспортёров;
- обновления API типов frontend.

## 6. Долгие операции являются задачами

AI-генерация, тяжёлый импорт, IFC и PDF обработка не должны держать HTTP-запрос
открытым длительное время. Целевая модель:

```text
POST task -> task_id
GET task status -> progress/result/error
```

## 7. Проверки прозрачны

Каждый validator возвращает:

- код проверки;
- статус;
- сообщение;
- входные значения;
- источник правила;
- геометрию нарушения, если применимо;
- уровень уверенности.

## 8. Production отличается от demo

Demo-функции могут существовать, но они:

- не входят в основной пользовательский сценарий;
- явно помечены;
- не влияют на утверждённые метрики;
- не считаются завершёнными без quality gate.

## 9. Технологические решения

Ближайшая фаза сохраняет текущий стек:

- Next.js и React для web UI;
- FastAPI и Pydantic для engine API;
- Shapely и ezdxf для 2D-геометрии и DXF;
- IfcOpenShell для IFC;
- SQLite и локальные файлы только для локального MVP;
- PostgreSQL и S3-совместимое хранилище до production beta.

Новые библиотеки добавляются только после проверки лицензии, поддержки и
реальной необходимости.
