Технический спайк под фокус-задачу C1 из [BI_PARTNERSHIP_PLAN.md](BI_PARTNERSHIP_PLAN.md).
Цель — оценить пути экспорта и дать рекомендацию, **не реализуя** ничего сейчас.

Вопрос BI (звонок 18.06.2026): «Экспорт DWG + Revit — приоритет, PNG/PDF мало».
Сравнивали с ПИК/«Самолёт»: генератор квартирографии с DWG/Revit + объёмный файл.

> ⚠️ Важный контекст из памяти проекта: BI требует Revit **с заполненными
> параметрами → объёмы/смета**. То есть «экспорт в Revit» для BI — это не просто
> геометрия, а нативная модель с параметрами, из которой считаются ведомости.
> Это меняет вывод (см. раздел 3).

## 2. DWG экспорт — простой случай

ezdxf принципиально не пишет DWG. Практический путь — **обратить уже
существующий мост**: мы конвертируем DWG→DXF при импорте; для экспорта нужно
DXF→DWG тем же конвертером.

**Рекомендация: переиспользовать `importers/dwg.py`.**

- ODA File Converter работает в обе стороны (на вход даём DXF, формат вывода —
  DWG-версия, напр. `ACAD2018`). `_find_converter()` уже умеет его находить.
- Добавить `dxf_to_dwg(dxf_bytes) -> bytes` рядом с `dwg_to_dxf()` (зеркало) и
  эндпоинт `POST /export/floorplan-dwg`, который: строит DXF существующим
  `build_floorplan_dxf()` → прогоняет через конвертер → отдаёт `.dwg`.
- LibreDWG для обратной конвертации менее зрелый — для экспорта полагаемся на ODA.

**Оценка:** ~1–2 дня + установка ODA File Converter на сервере. Без новых
зависимостей в Python. Риск низкий: переиспользуем проверенный код.

**Оговорка по лицензии:** ODA File Converter бесплатен для использования, но при
распространении в составе продукта нужно свериться с лицензией ODA / поставить
его как внешнюю зависимость в контуре BI (не вшивать в дистрибутив).

## 3. Revit экспорт — настоящий вопрос

Тут развилка, и от неё зависит трудоёмкость на порядок. «Экспорт в Revit» может
означать две очень разные вещи.

### R1. IFC → Revit (геометрия, **уже есть**)

Revit нативно импортирует/линкует IFC (Open IFC). Мы уже отдаём хороший IFC4.

- **Плюсы:** работает сегодня, ноль нового кода на нашей стороне. Архитектор BI
  открывает наш `.ifc` в Revit и видит геометрию (стены, перекрытия, помещения).
- **Минусы:** импортированный IFC приходит как **обобщённые элементы**
  (IfcWall→Generic), а **не нативные семейства Revit с заполненными
  параметрами**. Из такой модели **не считаются объёмы/смета по стандарту BI**.
- **Вывод:** закрывает «посмотреть в Revit», но **не закрывает** реальную
  потребность BI (подшивка → объёмы/смета).

### R2. Нативный Revit-адаптер (то, что реально нужно BI)

Скрипт/плагин на стороне Revit, который читает нашу каноническую модель
(`LayoutFloor` как JSON или наш IFC) и строит **нативные** стены/помещения/уровни
через Revit API, заполняя параметры по шаблону BI.

- **Технологии:** pyRevit / Dynamo (Python, быстрый прототип) либо C# add-in
  (продакшн, .addin). Обе используют Revit API → нативные семейства + параметры.
- **Плюсы:** даёт ровно то, что нужно BI — модель, из которой идут
  объёмы/спецификации/смета. Совпадает с линией Maxat: логика экспорта **вне
  движка**, отдельным компонентом (не тащим Revit-зависимости в backend; меньше
  риск при обновлениях).
- **Минусы / блокер:** требует **эталонный Revit-шаблон BI и стандарт
  параметров** (какие семейства, какие общие параметры обязательны). Это ровно то,
  что мы запросили в [BI_PARTNERSHIP_PLAN.md §5.1](BI_PARTNERSHIP_PLAN.md). Без
  него адаптер можно прототипировать на «угаданном» шаблоне, но не финализировать.
- **Оценка:** прототип pyRevit на нашем JSON — ~1 неделя; продакшн-адаптер с
  параметрами BI — после получения их шаблона.

### R3. Autodesk APS / Design Automation for Revit (облако) — **отклонить**

Headless-Revit в облаке Autodesk.

- **Минусы:** платная подписка Autodesk; данные уходят в облако Autodesk —
  **прямой конфликт с требованием СБ BI** «данные не уходят в global». Отклоняем
  для контура BI.

## 4. Рекомендация и порядок

1. **Сейчас (в вакууме, без данных BI):**
   - Сделать **DWG-экспорт** (раздел 2) — закрывает явный приоритет дёшево.
   - **Зафиксировать IFC→Revit (R1) как демо**: проверить открытие нашего `.ifc`
     в Revit, задокументировать, что это геометрия, а не нативные параметры. Это
     честный промежуточный ответ «да, в Revit открывается».
   - Описать **JSON-контракт `LayoutFloor`** для будущего Revit-адаптера и собрать
     прототип pyRevit (R2) на нашем шаблоне, чтобы доказать путь до получения
     стандарта BI.

2. **После получения от BI Revit-шаблона и стандарта параметров (§5.1 плана):**
   - Финализировать нативный Revit-адаптер (R2) под их семейства/параметры →
     модель, из которой считаются объёмы/смета.

**Не делать:** R3 (облако Autodesk) — несовместимо с СБ BI.

---

## 5. Что это требует от BI (связь с планом)

Нативный Revit (R2) — единственный путь, закрывающий реальную потребность BI, и
он **заблокирован их данными**:

- эталонный Revit-шаблон (.rte / пример .rvt);
- стандарт обязательных параметров (общие параметры, имена, единицы);
- какие именно ведомости/спецификации должны считаться из модели.

Эти пункты уже в запросе [BI_PARTNERSHIP_PLAN.md §5.1–5.2](BI_PARTNERSHIP_PLAN.md).
Спайк подтверждает: без них Revit-экспорт нельзя довести до «как у ПИК/Самолёта».
